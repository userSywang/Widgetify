# 灵感拖动问题分析（0.2.13）

用户已确认保存当前列表、展开、单条删除与恢复交互并替换本机版本。标题及空白偶发拖不动仍存在。后续只分析，未获得进一步修改授权。

## 已确认的代码问题

1. 拖动区域不是完整的标题栏。`InspirationPresentation.swift` 的标题背景、标题栏中间填充和四侧边缘分别注册区域。主内容留白22pt，顶部和底部只覆盖16pt，左右只覆盖14pt，因此分别存在6pt和8pt的未覆盖带；标题栏HStack还有12pt间距，没有整体拖动处理。这些视觉空白不会通过 `WidgetDragView.track` 的 `bounds.contains` 判断。
2. 灵感与快捷启动没有使用完全相同的拖动路径。快捷启动的 `positionKey` 为 nil，走 `mouseDown` → `performDrag`；灵感的 key 非空，在应用本地事件监听中消费按下、移动、抬起事件，再手动 `setFrameOrigin`。共享宿主并不等于共享拖动行为。
3. 上一轮多个监听器已合并为单窗口监听，但用户实测仍失败，因此“监听器相互抢事件”不能认定为该故障的完整根因。

## 尚未确认的部分

- 精确点中标题区域后失败，不能仅用空隙解释。
- 当前预览诊断仅记录按下与抬起，不记录移动、区域标识、坐标及事件时序；仅保留12条区域级记录。同一次按下可以产生多个未命中记录。因此不能从现有记录断言是“没收到移动”“窗口被原宿主拉回”或“未命中”。
- 回归测试直接调用处理器，覆盖状态与坐标运算，没有覆盖真实AppKit投递与原厂宿主事件处理。测试通过不能证明桌面拖动稳定。

## 后续建议（未实施）

先在隔离预览加入每次手势的完整时序诊断，区分：未命中可拖区、未收到移动事件、收到移动但窗口未移动、移动后被其他逻辑改回。仅记录坐标和事件，不记录灵感正文。拿到一次真实失败记录，再决定是合并标题栏可拖区，还是修正宿主事件转发。不要继续凭猜测更换拖动实现，也不要把原厂编译元数据称为源码。
